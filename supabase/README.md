# Supabase Phase 1 setup

This directory contains version-controlled database migrations. No credentials
belong here.

## 1. Create and connect the project

1. Create a Supabase project in the appropriate UK/EU region.
2. Copy the project URL, publishable key, and secret key into local/hosting
   environment variables using `.env.example` as the contract.
3. Apply `migrations/202609280001_phase1_auth_foundation.sql` either with the
   Supabase SQL Editor or the CLI:

   ```bash
   npx supabase login
   npx supabase init
   npx supabase link --project-ref YOUR_PROJECT_REF
   npx supabase db push
   ```

   `supabase init` only needs to be run once. Review and commit the generated
   `supabase/config.toml`; it must not contain production secrets.

The secret key bypasses RLS. Store it only in server-side environment settings.

## 2. Configure Auth

In Supabase Dashboard > Authentication:

1. Enable Email/Password authentication.
2. Disable public user sign-ups. Staff accounts must be created by an
   administrator through the Dashboard or, in a later phase, server-only admin
   code.
3. Set Site URL to the production `NEXT_PUBLIC_SITE_URL` value.
4. Add exact redirect URLs for:
   - `http://localhost:3000/auth/confirm`
   - `https://YOUR_PRODUCTION_DOMAIN/auth/confirm`
5. Configure a minimum password length of 12 and enable leaked-password
   protection if the selected Supabase plan supports it.
6. Configure production SMTP before relying on invites or password recovery.

For a token-hash based recovery link, set the recovery email button URL to:

```html
{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=recovery
```

For staff invitations initiated from the Dashboard, set the invite email button
URL to:

```html
{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite&next=%2Fstaff%2Freset-password
```

The application callback also accepts Supabase PKCE `code` callbacks. Redirect
destinations are allow-listed in application code and cannot target an external
site.

## 3. Bootstrap the first administrator

1. Apply the Phase 1 migration before creating the Auth user.
2. In Dashboard > Authentication > Users, create the administrator using their
   real email address and a unique password generated by a password manager.
   Do not place that password in the repository, SQL history, or chat.
3. The Auth trigger creates an `inactive` cleaner profile by default. In the SQL
   Editor, replace the email below and run:

   ```sql
   update public.profiles
   set role = 'admin'::public.app_role,
       status = 'active'::public.profile_status
   where id = (
     select id
     from auth.users
     where lower(email) = lower('ADMIN_EMAIL@example.com')
   );
   ```

4. Verify exactly one administrator was updated:

   ```sql
   select p.id, p.full_name, p.email, p.role, p.status
   from public.profiles p
   where lower(p.email) = lower('ADMIN_EMAIL@example.com');
   ```

5. Sign in at `/staff/login`. An active administrator is routed to `/admin`.

Every later Auth user starts as `cleaner/inactive`. This fail-closed default
prevents a newly created account from accessing protected pages until an
administrator explicitly activates it.

## RLS summary

- Anonymous users have no access to either Phase 1 table.
- Authenticated users can select their own profile, including an inactive
  profile so the application can deny it cleanly.
- Only an active administrator can select or update other profiles.
- Profile email is maintained from `auth.users`; browser clients cannot update
  it directly.
- Audit events are readable only by active administrators and cannot be
  inserted, updated, or deleted directly by browser clients.
